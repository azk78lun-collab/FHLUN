# Lun 更新规则与旧版恢复

## 固定约定

1. `main/lun.sh` 是主脚本；版本由实际脚本读取，不以 README、Release 标题或本机缓存判断最新版。
2. `main/upgrade.sh` 是长期保留的独立恢复入口。`LUN_UPGRADE_API=1`、`--target`、`--stage` 的含义保持向后兼容；不能重用文件名或破坏旧调用。
3. 菜单更新先取得 GitHub `main` 的最新提交，再按该不可变提交下载主脚本；核对 GitHub 文件对象标识、Shell 语法和版本。提交元数据无法获取、下载不符、限流或超时，只能报告“检查未完成”，不能显示“已是最新版”。
4. “已是最新版”要求实际命令入口与已验证的远端内容完全一致。同版本内容变化仍替换；拒绝降级。写入后复核 SHA-256、版本和实际入口，再重新加载菜单。
5. 下载器不能覆盖调用者的安装目标变量；所有辅助变量须限定作用域。升级文件不得与暂存文件相同。每次更新在目标目录原子替换，保留上一份脚本备份。
6. 更新主脚本不清空数据库、不生成新集群身份、不改 UUID、端口、证书或订阅令牌。主脚本版本与集群/多用户模块版本分开核对；“主脚本最新”不代表可选模块已更新。集群模块仍通过“更新与维护”更新并验证服务就绪。
7. 每次发布必须通过从旧版入口到新版的升级测试、同版本变更、错误元数据、下载失败、语法损坏、拒绝降级和重复执行测试；不得只测试全新安装。

## V26.10.20.3 的一次性恢复

该版本的下载函数未限定 `target` 作用域，会覆盖更新器的安装路径。之后暂存文件与自身比较，可能错误显示“当前已是最新版”。旧代码无法靠这个坏按钮修复自己，需要绕过一次。

以 root 登录 VPS，执行：

```bash
bash <(curl -fsSL -H 'Cache-Control: no-cache' "https://raw.githubusercontent.com/azk78lun-collab/FHLUN/main/upgrade.sh?nocache=$(date +%s)")
```

没有 curl 时：

```bash
bash <(wget -qO- "https://raw.githubusercontent.com/azk78lun-collab/FHLUN/main/upgrade.sh?nocache=$(date +%s)")
```

确认输出的“生效入口”和版本，再运行 `lun`。后续继续使用“服务与更新 → 更新本机 Lun 脚本”，无需卸载重装。

恢复脚本不依赖 Python，不重建代理配置，不主动加入/删除联邦成员。下载失败保留原文件；备份保存在实际入口旁的 `.update-backup` 文件中。

## 旧联邦与新成员

集群程序 `0.3.5` 修复历史导入顺序：当先收到撤销墓碑、再收到其他成员签发的旧成员介绍时，仍需保存该成员的历史验签证书，但必须同时记录撤销时间和序号边界，不允许进入活动信任包、成员列表或订阅。原节点 ID 和编号不重建，撤销边界后的新事件继续拒绝。

遇到“事件作者未受信任”时，不应清空数据库或删除全部成员。先升级发起端和接收端集群程序，再使用保留的配对恢复流程；确需新加入令牌时仅重新生成一次性地址。主脚本更新按钮故障与事件信任校验故障属于不同层，需要分别验证。
